# 上位机怎么把图片处理成 E6 能显示的格式

> 适用：佳显 GDEP133C02（13.3"）/ GDEB0709E01（7.09"），1200×1600、4bpp、6 色
> 本文的规格是**从官网在线工具 <https://www.e-paper-display.com/bmp.html> 的前端 JS 逆向出来的**，可直接照此实现；配套脚本 `host/e6_convert.py`

---

## 1. 一句话：屏只认一种数据，所有"处理"都在上位机

固件里没有任何缩放、旋转、翻转、抖动代码（两份官方示例都验证过），它只做一件事：**把 960 000 字节原样丢给面板**。所以上位机要产出的是：

```
1200 × 1600 像素 → 6 色抖动 → 每字节 2 像素（4bpp，高 nibble 在左）→ 960 000 字节
```

一帧 = 960 000 B ≈ 0.92 MB。这决定了容量：16 MB Flash 大约放 15 帧（官方 USB 工具就是 Image1–15），SD 卡则随便放。

---

## 2. 官方三条工具链，各管一段

| 工具 | 跑在哪 | 处理什么 | 产物 |
|---|---|---|---|
| 在线转换器 `bmp.html` | 浏览器 | 拉伸、6 色抖动、打包 | `.bin`（带帧头）、`.bmp` 预览、`.hex` 文本 |
| Spectra 6 Rendering Tool v2.8.1 | Windows | 调图 + 抖动 + 模拟预览 | 散点图，再经 Image Tool 烧进 Flash |
| Spectra 6_Image_Tool | Windows | USB 烧图 | 把已抖动好的 1200×1600 图写进板载 Flash 的 Image1–15 |
| NeoFrame App | 手机 | 拍照/相册直传，App 内抖动 | 走 WiFi 推给开发板 |

**关键：抖动只做一次。** 三个工具输出的都是"已抖动、已打包"的数据，谁都不在设备端再处理——所以**别把原始 JPG 直接塞给固件**。

## 3. 可直接实现的规格（逆向结果）

### 3.1 分辨率与画幅

- 面板 1200 × 1600（竖屏 3:4）。官网工具对图片的处理是 **直接拉伸铺满**（`drawImage(img,0,0,W,H)`，不保持比例），所以横图会被压扁。**实际项目建议用等比裁剪（cover），不要拉伸。**

### 3.2 调色板（这是关键，别用纯 RGB 去抖）

官网 JS 里有两块表：

| 索引 | 面板实测色 REAL_PALETTE | 4bit 像素码 |
|---|---|---|
| 0 | `(255,255,255)` 白 | `0x1` |
| 1 | `(0,0,0)` 黑 | `0x0` |
| 2 | `(160,32,32)` 红 | `0x3` |
| 3 | `(240,224,80)` 黄 | `0x2` |
| 4 | `(80,128,184)` 蓝 | `0x5` |
| 5 | `(96,128,80)` 绿 | `0x6` |

抖动是**对着"实测色"算误差**的，不是对着纯 `#FF0000` 算——这是很多自己写转换器的人画面发脏的根因。E6 的红偏砖红、蓝偏灰蓝、绿偏橄榄绿，用纯色当目标会让误差扩散到错误方向。

### 3.3 抖动算法（权重与官网一致）

| 名称 | 说明 |
|---|---|
| `floyd` | 标准 Floyd–Steinberg（7/16, 3/16, 5/16, 1/16） |
| `fs-ser` | 蛇形 Floyd–Steinberg（**官网默认、推荐**，消除规则条纹） |
| `atkinson` | 6 个 1/8，只扩散 3/4 误差，对比更硬、亮部更干净 |
| `stucki` | 权重和 42，比 FS 细腻、速度慢 |
| `jjn` | Jarvis–Judice–Ninke，权重和 48，颗粒最细但容易"发糊" |

误差扩散后必须 **clamp 到 0..255**（官网用的是 `Uint8ClampedArray`，靠类型自动钳位，自己实现时容易漏）。

### 3.4 打包规则

- 行优先、从上到下、从左到右；
- 每字节两个像素，**高 nibble = 左边那个像素**；
- 像素码按上表：黑 0、白 1、黄 2、红 3、蓝 5、绿 6（4、7 不用）；
- 整帧 `1200 × 1600 / 2 = 960000` 字节，**不切左右半屏**——左右分片是固件发数据时做的事（每行 600 B 里前 300 B 给主 IC、后 300 B 给从 IC）。

### 3.5 `.bin` 容器格式（SD 卡固件用）

```
偏移 0   : "EPD6BIN\0"        8 B   magic
偏移 8   : uint16 width       2 B   LE = 0x04B0 (1200)
偏移 10  : uint16 height      2 B   LE = 0x0640 (1600)
偏移 12  : uint16 frames      2 B   帧数
偏移 14  : uint32 interval_ms 4 B   轮播间隔
偏移 18  : 帧数据 × frames     每帧 960000 B
```

实测生成的 bin 前 18 字节：

```
4550 4436 4249 4e00 b004 4006 0100 9600 0000
E P D 6  B I N \0  1200 1600  1   150ms
```

### 3.6 C 数组（编译进固件用）

```c
const unsigned char gImage[960000] = { 0x33, 0x33, ... };   // 直接按字节序拷
```

注意：**不同工具的方向约定可能不一致。** 官网网页工具是标准"左上角起始、行优先"；而 13.3" 示例包里的 `image.h` 解出来是旋转 180° 的构图（见 `analysis.md` §7）。所以自建管线后第一次点亮，务必先刷 §4 的自检图确认方向。

## 4. 配套脚本：`host/e6_convert.py`

一个文件，只依赖 pillow + numpy，实现上面全部规格，并带自检/解码/自检图生成。

```bash
# 本目录下执行；Python 用工作区根目录的共享环境 ../../.venv（全工作区唯一一套）
# 1) 单图 → bin + C 数组 + 预览（默认 1200x1600、fs-ser、等比裁剪）
../../.venv/bin/python host/e6_convert.py photo.jpg --fit cover \
        -o host/samples/photo.bin --header host/samples/photo_image.h --preview host/samples/photo.png

# 2) 多图 → 一个多帧 bin（固件按 interval 轮播）
../../.venv/bin/python host/e6_convert.py a.jpg b.jpg c.jpg -o host/samples/images.bin --interval 150

# 3) 方向自检图（第一次点亮必做）
../../.venv/bin/python host/e6_convert.py --test-pattern -o host/samples/test.bin --header host/samples/test_image.h

# 4) 反向验证：bin 解回 PNG，确认字节与预期一致
../../.venv/bin/python host/e6_convert.py --decode host/samples/photo.bin -o host/samples/photo_back.png
```

实测耗时：整帧 1200×1600 **约 3.7 s**（纯 Python 串行误差扩散），产物体积 960 018 B。

参数：

| 参数 | 取值 | 建议 |
|---|---|---|
| `--fit` | `stretch` / `cover` / `contain` | 用 `cover`（等比裁剪），官方 `stretch` 会把横图压扁 |
| `--dither` | `fs` `fs-ser` `atkinson` `stucki` `jjn` `none` | 照片用 `fs-ser`；文字/图表用 `none`（硬量化，字更锐） |
| `--strength` | 0..1 | 0.7–1.0；调低可减少颗粒感但会丢层次 |
| `--rotate` / `--flip` | 90/180/270、`h`/`v` | 只为修正素材方向，**不要用来纠正上屏镜像**（那是固件/方向约定问题） |
| `--interval` | ms | 与固件轮播间隔一致（E6 建议 ≥150 s 翻页，别设 150 ms） |

## 4.5 这块屏到底能显示多少种颜色

**像素级：6 种，没有灰阶。** 每个像素只能是 黑/白/红/黄/蓝/绿 之一，4bpp 只是编码宽度（16 个码位，`0x4`/`0x7` 保留不用）。两份官方 `image.h` 共 192 万像素，实际出现的 nibble 只有 `0,1,2,3,5,6` 六种，无一例外。

**表观级：靠抖动混色，可辨色约几百种。** 按面板实测色的 Lab 坐标聚类（ΔE76 > 5 视为可辨）：

| 抖动单元 | 混合组合数 | 可辨色数 |
|---|---|---|
| 2×2（4 px） | 126 | 101 |
| 3×3（9 px） | 2 002 | 410 |
| 4×4（16 px） | 20 349 | 643 |
| 5×5（25 px） | 142 506 | 792 |

单元越大色越多，但颗粒也越明显；150 PPI 下 2×2 单元 ≈ 0.34 mm，正常阅读距离已可见。

常见"Spectra 6 支持 54 600 色"的说法来自经销商术语表（如 [displaynd](https://displaynd.de/Glossar/E-Ink-Spectra/)），属于组合数口径，不是像素能力，也未见于 E Ink 一手资料。

**实测 14 个目标色的还原度**（抖动后平均色 vs 目标色，RGB 平均偏差）：

| 目标色 | 抖动后 | 偏差 | 配色比例 |
|---|---|---|---|
| 橙 (230,120,40) | (197,120,54) | 15.8 | 红 54% + 黄 46% |
| 紫 (120,70,150) | (107,96,133) | 18.7 | 红 33% + 蓝 67% |
| 青 (60,150,160) | (84,128,160) | 15.2 | 蓝 77% + 绿 23% |
| 粉 (220,150,170) | (176,150,165) | 16.4 | 白 40% + 红 31% + 蓝 28% |
| 棕 (120,80,50) | (120,80,55) | 1.8 | 红 44% + 绿 51% |
| 藏蓝 (40,50,90) | (40,64,90) | 4.6 | 黑 50% + 蓝 48% |
| 金 (200,170,60) | (200,170,71) | 3.5 | 黄 63% + 红 20% + 绿 17% |
| 浅灰 (200,200,200) | (189,200,200) | 3.8 | 白 48% + 蓝 35% + 黄 14% |

![六原色与抖动混色实测](host/samples/gamut-dither.png)

**结论**：暖色（棕/金/橙）和深色（藏蓝）能凑合；紫、青、粉这类"要第三种颜料参与"的颜色最差，会明显发灰、发脏。所以 E6 适合海报式的大色块构图，不适合照片级肤色和渐变背景。

## 5. 三条投放路径怎么对接

| 路径 | 你要交出的文件 | 注意事项 |
|---|---|---|
| **SD 卡** | `images.bin`（§3.5 格式）拷到卡根目录 | 固件是否解析 `EPD6BIN` 头取决于固件版本；先拿官方 `.bin` 试一次，能播就把自己生成的塞进去 |
| **USB 上位机（Image Tool）** | 已抖动好的 1200×1600 图（工具自己会打包），或直接把 `.bin` 的帧数据按 Image1–15 写入 | 该工具只认抖动后的图/字节流，塞原图会花 |
| **C 数组编译进固件** | `image.h`（脚本 `--header` 直接生成） | 960 KB 会占满 app 分区；16 MB Flash 建议放 3–5 帧 + 其余走 SD |
| **WiFi / NeoFrame** | 不需要你处理 | App 里选 6 色 + 抖动算法实时算 |

## 6. 参数怎么调（实战经验）

1. **先裁剪再抖动**。3:4 以外的图用 `cover`；海报类按内容重心裁，别用拉伸。
2. **提升饱和度**。E6 的蓝（`80,128,184`）和绿（`96,128,80`）本身就灰，原图偏淡时先 +15~25% 饱和度再抖，观感会明显好。
3. **文字别用误差扩散**。会扩散出彩色毛边，用 `--dither none` 或先二值化；中文小字（<24 px）在 150 PPI 上必然糊，能少用就少用。
4. **人脸别用 Atkinson**。Atkinson 亮部干净但暗部丢层次，肤色容易糊成色块；人像用 `fs-ser` 或 `stucki`。
5. **强对比图（框图/Logo）用 `none`**，色块边缘干净；照片类才上扩散。
6. **别迷信 6 色**。深蓝/紫在 E6 上没有对应色，会抖成"蓝+黑+红"的杂点，能避开就避开。

## 7. 上屏验收 / 排错清单

| 现象 | 原因 | 处理 |
|---|---|---|
| 画面上下颠倒 | 数据方向约定与固件相反 | 用自检图确认，然后 `--rotate 180` 或 `--flip v` |
| 画面左右镜像 | 同上（水平） | `--flip h` |
| 左半/右半错位、撕裂 | 自己实现时按整行 600 B 一次性发给单颗 IC | 必须每行前 300 B→主 IC、后 300 B→从 IC |
| 整体偏灰、发脏 | 抖动目标用了纯 RGB 而不是实测色 | 用 §3.2 的 REAL_PALETTE |
| 出现规则斜纹 | 标准 FS 的方向性伪影 | 换 `fs-ser` 蛇形 |
| 底部一条白线/顶部错行 | 宽高设反（1600×1200） | 面板是 1200 宽 × 1600 高 |
| 颜色数量不对（只见 4 色） | 图片本身饱和度低，抖不出红/黄 | 先提饱和度，或换对比更强的素材 |

10 分钟验收法：刷自检图 → 确认红块在左上、绿块在右下、顶部文字可正读 → 再刷真实照片。

## 8. 核心代码（约 25 行看清楚）

```python
PALETTE = np.array([[255,255,255],[0,0,0],[160,32,32],[240,224,80],[80,128,184],[96,128,80]], np.float32)
CODE    = np.array([0x1, 0x0, 0x3, 0x2, 0x5, 0x6], np.uint8)   # 调色板索引 → 面板像素码

img = Image.open(p).convert("RGB").resize((1200, 1600), Image.LANCZOS)   # 生产环境建议等比裁剪
buf = np.asarray(img, np.float32).copy()
idx = np.zeros((1600, 1200), np.uint8)

for y in range(1600):                                  # 蛇形 Floyd–Steinberg
    ltr = (y % 2 == 0)
    for x in (range(1200) if ltr else range(1199, -1, -1)):
        px = buf[y, x]
        i  = int(((px - PALETTE) ** 2).sum(1).argmin())  # 最近色（示意写法，慢）
        err = px - PALETTE[i]
        buf[y, x] = PALETTE[i]
        idx[y, x] = i
        step = 1 if ltr else -1
        for dx, dy, w in [(1, 0, 7/16), (-1, 1, 3/16), (0, 1, 5/16), (1, 1, 1/16)]:
            nx, ny = x + dx * step, y + dy
            if 0 <= nx < 1200 and ny < 1600:
                buf[ny, nx] = np.clip(buf[ny, nx] + err * w, 0, 255)

codes  = CODE[idx]                                     # HxW 面板码
packed = ((codes[:, 0::2] << 4) | codes[:, 1::2]).tobytes()   # 960000 B，高 nibble 在左
```

上面这段是"能读懂"的版本（逐像素 argmin，全图要几分钟）；实际工程里用内联最近色判断 + 扁平 `array('f')` 缓冲，整图 **3.7 s**，完整实现见 `host/e6_convert.py`（约 400 行，含多算法、bin 头、解码回 PNG、自检图生成）。

## 9. 尚未验证 / 需要实机确认

1. **SD 固件是否严格解析 `EPD6BIN` 头**——网页工具导出带头的 bin，但我没有固件源码，无法确认它读不读 interval/frames 字段；先用官方 bin 试。
2. **方向约定**：网页工具是标准行优先，13.3" 示例 `image.h` 却是 180°，两者不一致（见 `analysis.md`）。**以自检图实测为准。**
3. 官方 Windows 工具的调图参数（对比度/饱和度曲线）未逆向，脚本里没有等价实现。
