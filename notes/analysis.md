## 1. 一句话结论

| 工程 | 本质 | 可直接用吗 |
|---|---|---|
| 13.3" 示例 | **E Ink 原厂参考设计**（多屏共用、Windows + IDF 4.4.4 编译），保留了大量无关代码（USB CDC、HTTPS 证书、局部窗口、彩条/棋盘测试） | 能点亮，但代码脏、无休眠、每帧刷 4 次屏，只能当参考 |
| 7.09" 示例 | **厂家二次整理的"纯点屏"工程**（IDF 5.4.4 + Arduino 双环境，无网络/轮播），结构干净、有注释、有 sleep | 推荐作为移植基线 |

两者的**面板驱动思路完全一致**（双 CS、左 600 列 + 右 600 列、每行 300 字节、DTM 每半个屏只发一次），差别集中在工程整洁度、初始化参数、SPI 速率与休眠处理上。

## 3. 引脚与外设（两块板同一套 pinout）

| 信号 | 13.3" 示例 | 7.09" 示例 | 说明 |
|---|---|---|---|
| SCLK | IO9 | IO9 | 一致 |
| MOSI / D0 | IO41 | IO41 | 一致 |
| MISO / D1 | IO40 | IO40 | 一致 |
| D2 / D3 | IO39 / IO38（已定义，**未启用**） | — | 13.3" 预留了 QSPI 4 线 |
| CS_M（主区） | IO18 | IO18 | 一致 |
| CS_S（从区） | IO17 | IO17 | 一致 |
| RST | IO6 | IO6 | 一致 |
| BUSY | IO7 | IO7 | 一致 |
| DC | **无**（用 8 位命令相位代替） | IO2 | 关键差别 |
| 面板电源/负载开关 | IO45（`LOAD_SW`，上电即拉高，从不关闭） | IO45（`EPD_PWR`，休眠时拉低） | 关键差别 |

**结论：ESP32-133C02-IL 这一块板能同时点 7.09" 和 13.3"，两份示例的 GPIO 完全兼容**，换屏只需换驱动文件和 image.h。

## 4. SPI 驱动方式（两份都用单线，QSPI 没启用）

| 项 | 13.3" | 7.09" |
|---|---|---|
| 控制器 | `SPI3_HOST` | `SPI2_HOST` |
| 速率 | **10 MHz** | **20 MHz** |
| 线数 | 只配了 `data0/data1` → 单线 SPI | 单线 SPI（mosi/miso） |
| 命令方式 | `command_bits=8`，命令走硬件命令相位（`trans.cmd`），无 DC 引脚 | 软件拉 DC 低 + 发 8 bit 数据 |
| CS | GPIO 手动控制（`spiCsPin[2]`） | GPIO 手动控制（`spics_io_num=-1`） |
| DMA | `SPI_DMA_CH_AUTO`，单次上限 32 KB | DMA 缓冲 300 B，逐行发送 |
| 一次刷图的事务数 | 每半屏 1 次 `DTM` + 分块流式发送（32 KB/次） | 每半屏 1 次 `DTM` + **1600 次** 300 B 小事务 |

**纠正上一版调研报告的一处说法**：这两个官方工程虽然硬件上具备 QSPI 四线能力（其余引脚都引出来了），但**示例代码里 QSPI 并未启用**，实际都是单线 SPI。按 10 MHz / 单线算，整屏 960 000 字节传输约 **0.77 s**（7.09" 在 20 MHz 下 ≈0.4 s），相对 12–19 s 的波形刷新时间可以忽略——**刷新耗时瓶颈在波形而不在接口带宽**，这也解释了为什么佳显和微雪在"QSPI vs SPI"上的差异没有体现在刷新时间上。

## 5. 初始化序列逐条 diff（同命令、不同参数）

| 命令 | 13.3" GDEP133C02 | 7.09" GDEB0709E01 | 差异含义 |
|---|---|---|---|
| 0x74 AN_TM | `C0 1E 1E CE CE CE 15 15 55` | `00 0C 0C D9 DD DD 15 15 55` | 模拟时序，与面板/波形绑定，必须整组照抄 |
| 0xF0 CMD66 | `49 55 13 5D 05 10` | 同 | 一致 |
| 0x00 PSR | `DF 69` | `DF 6B` | 差 1 bit（扫描/数据顺序） |
| 0x50 CDI | `F7` | `37` | 驱动电流/占空设置 |
| 0x60 TCON | `03 03` | 同 | 一致 |
| 0x61 TRES | `04 B0 03 20` | 同 | 0x04B0=1200，0x0320=800 → 分辨率=1200×1600 的依据 |
| 0xE3 PWS | `22` | 同 | 一致 |
| 0xE0 CCSET | `01` | 同 | 一致 |
| 0x86 AGID | `10` | 同 | 扫描方向 |
| 0x01 PWR | `0F 00 28 2C 28 38` | 同 | 一致 |
| 0xB6 EN_BUF | `07` | 同 | 一致 |
| 0x06 BTST_P | `E8 28` | `E0 20` | 升压参数 |
| 0x05 BTST_N | `E8 28` | `E0 20` | 升压参数 |
| 0xB7 BOOST_VDDP_EN | `01` | 同 | 一致 |
| 0xB0 BUCK_BOOST_VDDN | `01` | 同 | 一致 |
| 0xB1 TFT_VCOM_POWER | `02` | 同 | 一致 |
| 0x30 PLL | **缺** | `08` | 7.09" 多了帧率设置 |
| 0x03 POFS | **缺** | 主 `00 C0 03 A8` / 从 `00 C0 03 9A` | 7.09" 单独校准两颗 IC 的 VCOM 偏移 |
| 0xA5 DCDC | **缺** | `44 54 00` | 7.09" 显式配置 DC-DC |
| 0xA4 CMDA4 | **缺** | `03 00 01 03 00 03 00 00 00` | 7.09" 额外寄存器组 |
| 0x12 DRF | `01` | `00` | 刷新参数 |
| 0x02 POF | `00` | `01` | 掉电参数 |

**重要结论**：
1. 命令集相同，**参数按尺寸/批次独立调校**，不是简单改分辨率就能换屏。
2. 7.09" 的序列比 13.3" **更完整**（多了 PLL / POFS / DCDC / CMDA4），说明 13.3" 那份是较早的参考设计。
3. POFS 主从不同 → **两颗 IC 的 VCOM 要分别校准**，13.3" 示例没做这一步，是它画面一致性可能不如新版固件的原因之一（待实测）。

## 6. 刷图流程（两份一致）

```
复位 → 初始化（20 条左右私有命令）→
  CS_M 拉低 → DTM(0x10) → 1600 行 × 300 B（左半）→ CS_M 拉高
  CS_S 拉低 → DTM(0x10) → 1600 行 × 300 B（右半）→ CS_S 拉高
→ PON(0x04) 等 BUSY
→ DRF(0x12) 等 BUSY（≈12–19 s）
→ POF(0x02) 等 BUSY
→ （7.09"）0x02+0xA5 → 拉低 PWR 断电
```

**双 IC 三条铁律**（代码里都体现）：
1. `DTM(0x10)` 每颗 IC **只发一次**，发送期间 CS 必须保持低电平，中途松开就整屏错位。
2. 命令分两类：**公用命令**（PSR/TCON/TRES/PWS/AGID/CMD66 等）两颗 IC 同时选中（`cs_all(0)`），**独立命令**（AN_TM/POFS/PWR/BTST/DCDC 等）只选主区或从区。
3. 数据按"左半 600 px → 右半 600 px"切，每行 600 B 中的前 300 B 给主区、后 300 B 给从区。

## 7. 数据格式：两份 image.h 完全同构

| 项 | 值 |
|---|---|
| 数组长度 | 960 000 字节 = 1200 × 1600 / 2 |
| 位深 | 4 bit/pixel，1 字节 2 像素（高 nibble 在左） |
| 调色板 | 0=黑、1=白、2=黄、3=红、5=蓝、6=绿（4、7 未用） |
| 抖动 | 已在 PC/手机端完成，固件里**没有任何**重采样、旋转、翻转、抖动的代码 |
| 实测色占比（13.3" 样例） | 黑 10.0%、白 32.6%、黄 6.7%、红 10.8%、蓝 21.9%、绿 18.0% |
| 实测色占比（7.09" 样例） | 黑 12.8%、白 24.1%、黄 2.8%、红 10.9%、蓝 41.9%、绿 7.5%（右下角带一枚二维码水印） |

我把两份 `image.h` 解码成 PNG 验证（`docs/preview/decode_*.png`）：

- 7.09" 样例解码后右下角的二维码是正的 → 它是标准"左上角起、行优先"顺序；
- 官网在线转换器（`bmp.html`）的 JS 也明确是"左上角起、行优先、高 nibble 在左"（见 `host-pipeline.md` §3.4），与 7.09 样例一致；
- 但 13.3" 样例按同样顺序解码后画面是倒的（旋转 180° 才自然）→ 它大概率出自早期的 Windows 渲染工具，方向约定与现在的网页工具不同。

**结论：官方现行约定是标准顺序，但历史样例不统一。** 自建出图管线后，第一次点亮务必先刷一张带"左上角红块 + 顶部文字"的自检图确认方向（`host/e6_convert.py --test-pattern`）。

**结论：固件端永远"照抄字节、不做任何变换"**，方向/镜像/抖动全部在上位机出图时定死；而不同工具的方向约定并不统一，所以自己写上位机时，必须先用一张自检图（二维码/文字/异色角块）验证方向，再批量出图。

## 8. 两份代码的差异清单

| 维度 | 13.3" 参考设计 | 7.09" 整理版 | 建议 |
|---|---|---|---|
| 休眠 | `epdDisplay()` 只发 POF，**从不深睡、不断电**，`app_main` 刷完 4 图后 `while(1);` | `POF + 0xA5` 后拉低 PWR，真正掉电 | 抄 7.09" 的 |
| 复位 | 拉低 20 ms → 拉高 20 ms | 高 30 → 低 30 → 高 30 → 低 30 → 高 30（三段脉冲） | 抄 7.09" 的（更稳） |
| BUSY 等待 | `while(!gpio_get_level(BUSY));` **死等、无超时、无让出 CPU** | 10 ms 轮询 + 20 ms 余量 | 抄 7.09"，再加超时保护 |
| 局部刷新 | 有 `PTLW(0x83)` 局部窗口实现（x 起点须 8 对齐、宽 ≥32 px、单 IC ≤600 px） | 无 | E6 波形不支持快速局刷，窗口刷也仍是全波形，不要当卖点 |
| 测试图 | 彩条 / 照片 / 棋盘 / 白屏，4 次全刷 | 1 张图 + 可选刷白 | — |
| 每行延时 | 照片发送时每行 `delayms(1)`（FREERTOS_HZ=100 下实际为 0 tick，等于没延） | 无延时 | 都无实际影响，但 13.3" 这段代码会误导人 |
| 代码卫生 | 残留 USB CDC、HTTPS 根证书、`component.mk`、注释里还有 800×720 的旧屏参数 | 干净，注释完整，README 讲清数据布局 | 抄 7.09" 的 |
| 错误处理 | 基本无（`assert` + 死等） | 全 `esp_err_t` 返回并检查 | 抄 7.09" 的 |
| Arduino 支持 | 无 | 有（`SPIClass(FSPI)` + `writeBytes` 走 DMA） | 需要 Arduino 就用 7.09" 那份 |

## 9. 移植到自己板子上的最小清单

1. **引脚映射**：SCK/D0/D1/CS_M/CS_S/RST/BUSY 七根线必须对上；DC 可有可无（有则走 4-wire SPI，无则用 8-bit 命令相位），QSPI 四线可选（需自行改 `spi_bus_config` 的 `data2/data3` 并把速率/相位调对）。
2. **初始化参数整组照抄**：不要拿 7.09" 的参数去点 13.3"，反之亦然；AN_TM / PSR / BTST / PWR 任一组不对，轻则发灰重则不出图。
3. **双 CS 时序**：公用命令两颗 IC 同时选中，AN_TM/POFS/PWR 等只对主区发；DTM 之后 CS 全程拉低。
4. **缓冲策略**：整屏 960 KB。ESP32-S3 有 8 MB PSRAM 可直接放整图；无 PSRAM 的型号（如 7.09" 的 8 MB Flash 配置）必须分块流式发送，不能 `malloc(960000)`。
5. **电源**：刷屏瞬间峰值 ≈1 A，USB 供电要留余量；面板 PWR 开关建议由 GPIO 控制，休眠时彻底断电。
6. **休眠**：显示完成 → `POF(0x02) + 0xA5` → 拉低 PWR。注意规格书写的是 `0x07 + 0xA5` 深睡命令，两份示例用的都是 `0x02 + 0xA5`，语义不等价，需要用电流表实测确认到底进了哪种状态。
7. **方向校验**：第一次点亮先刷"二维码 + 文字"图，确认没有镜像/倒置，再接抖动管线。

## 10. 还没弄清 / 需要向 FAE 确认的点

1. `POF(0x02)+0xA5` 与规格书 `0x07+0xA5` 的差别，实测待机电流到底是不是 0.7 µA。
2. 7.09" 的 PLL/POFS/DCDC/CMDA4 是否为 13.3" 也适用（大概率适用，但需厂家确认，因为 13.3" 样例没有）。
3. 13.3" 样例的 `PTLW` 局部窗口刷新实际效果（是否真的只刷窗口、残影如何）。
4. 两份样例都没有温度补偿代码，宽温场景的波形分档方案未提供。
